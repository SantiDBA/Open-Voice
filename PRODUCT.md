# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

One person: the owner, using it at their own machine, in short sessions, daily. Not a shared or
multi-tenant deployment, and not a demo surface. The interface can assume a user who already knows
what it is, does not need onboarding, and benefits from information density rather than explanation.

## Product Purpose

A speaking AI agent you converse with out loud. You activate it, talk, it transcribes, answers in
its own voice while you watch the text appear, and you can start talking over it to cut it off
mid-sentence. Success is a real hands-free conversation that feels immediate and that never loses
your words.

## Positioning

Everything runs on the user's own machine: speech recognition and speech synthesis are local
models, and the browser, the agent and the speech service all run on that machine. Only the
conversation text leaves, and it goes to a local routing daemon that picks a provider. A hosted
voice API cannot truthfully make that claim.

The mechanism worth stating plainly: interruption is real, not cosmetic. Starting to speak aborts
the language model stream, the speech synthesis and the browser playback, and late events are
discarded rather than appended.

## Operating Context

The microphone is activated explicitly, by the user, never ambiently. Two controls exist today:
Live mode, which streams continuously while active, and push to talk.

The user is at a desk, often with speakers. There is no acoustic echo cancellation, so the
microphone can hear the agent answering; headphones are the expected way to use it. A silent room is
the hard case: idle noise has been measured above the speech threshold, which makes the detector
trigger on nothing.

The stack is run with `docker compose`, four services, on a machine with no GPU. The browser is
Chromium-based and microphone capture needs explicit permission. Conversation history exists only
for the current connection; reopening the page starts empty.

## Capabilities and Constraints

Confirmed capabilities:

- Voice turn-taking with adaptive silence detection in the browser, including a short pre-roll so
  the first syllable is not lost.
- Interruption: speaking over a reply stops it.
- Live transcripts while speaking, streamed reply text, and spoken replies.
- Text input and an on-screen transcript of the dialogue. **Both must remain.** The voice path is the
  primary one; the text path is a required companion, not a leftover.
- Latency instrumentation is surfaced: per-turn timings and the live activity detector state.

Hard constraints:

- Speech recognition runs as whole-turn transcription, not streaming token-by-token, so the cost
  sits after the user stops speaking. Real streaming is not available on the local provider.
- No cross-session memory. History dies with the connection.
- No authentication and no multi-user isolation. Localhost only.
- Quality-sensitive tuning decisions are already settled by measurement and should not be revisited
  casually: speech-recognition model size is latency on this machine, and the silence grace before a
  turn closes cannot be shortened without cutting off the user's last word.

Open decisions and dependencies:

- **The agent is intended to act on the system, and cannot yet.** Tool calling and function calling
  do not exist in the backend. The product intent is confirmed by the owner; the capability is an
  open dependency on a backend increment. No interface may imply a capability the backend lacks.

## Brand Commitments

The project is named **Open Voice**.

The owner supplied a binding directional reference for the interface: a JARVIS-like autonomous
speaking assistant, strongly graphical, modern and dynamic. Record it as the brief, not as a
resolved visual world.

## Evidence on Hand

- Measured latency for every stage of a turn, recorded in `docs/runbook.md` section 10.
- Verification evidence for the provider stack and for browser acceptance, in `odd/tasks/`.
- Working speech synthesis in both Spanish and English, generated by the project's own local model.
- Vendored upstream documentation describing the session layer, in `THIRD_PARTY.md`.

Deliberate absences that future work must not fabricate: no user research, no usage analytics, no
testimonials, no benchmarks against another product, no pricing or deployment claims, and no brand
assets of our own. The vendored upstream logos were pruned and must not be reintroduced as if they
were ours.

## Product Principles

1. The voice path is the product. Text and transcript support it; they do not compete with it.
2. Never imply a capability the backend does not have. An interface that overstates is worse than a
   plain one.
3. Latency is a feature, and the instrumented measurements are the authority over intuition. A
   change that trades accuracy for speed without a measurement is a regression.
4. The user's words are the input of record. Anything that risks clipping, dropping or mangling a
   spoken word outranks any latency gain.
5. Local by default, and honest about the one thing that leaves: the conversation text.
